## 1. 结论先行

**下一版应优先解决快捷键作用域和操作提示，不应因历史记录而直接重写拖放或 PTY。**

本轮得到三条关键结论：

1. **观察到 F5 快捷键冲突。** 在跨窗口移动完成后按 F5，桌面目录完成刷新，但 VS Code 同时弹出调试选择器。已取消，没有选择调试程序或启动调试。
2. **真实跨窗口移动在本次场景通过。** 使用前台鼠标将一个带中文、空格名称的测试文件从 `source` 拖到 `target`；源目录不再显示该文件，目标目录显示该文件，刷新后状态保持。
3. **终端中文多行粘贴和保存链路可用，但快捷键必须区分。** 普通 Ctrl+V 在 Vim 中表现为控制键 `^V`；Ctrl+Shift+V 成功贴入英文、中文及换行。随后 Vim 保存为新文件，VS Code 重新打开后内容正确。

上述结论是有条件的真实 UI 观察，不代表所有输入方式、拖放组合、网络情况和规模场景均已通过。

## 4. 优先修复：F5 与宿主快捷键冲突

### 本次观察序列

1. 在真实 Remote-SSH Webview 打开 source、target 两个详情窗口。
2. 将本轮新建文件拖入 target，等待目录更新。
3. 在随后界面状态下按 F5。
4. 底栏显示目录刷新完成，但 VS Code 同时弹出包含 Node.js、Python Debugger、Web 应用等选项的调试选择器。
5. 按 Escape 取消，未继续选择任何调试项。

证据：[F5 后的画面](../artifacts/mcp-ui-20260917-b73f/29-drop-refreshed.png)、[取消后](../artifacts/mcp-ui-20260917-b73f/30-debug-picker-cancelled.png)。

**预期：** 在桌面文件管理区域执行刷新时，不应意外触发宿主调试入口。

**判断边界：** 本轮观察到一次该序列，尚未穷举焦点位于条目、空白区、地址栏或终端时的差异。不能表述为“所有 F5 场景都会失败”。

### 定位与建议

当前 `media/desktop.js:1069–1086` 在文档级处理快捷键；F5 分支只调用 `preventDefault()` 和 `refreshAll()`。这提供了排查入口，但不能仅凭静态代码就断言一条 `stopPropagation()` 可以解决所有 VS Code 宿主分发问题。

建议下一项开发任务：

- 在真实 Webview 中区分宿主键绑定、DOM 事件传播、焦点恢复和终端按键链路。
- 以实际可用的 VS Code 焦点上下文限制快捷键作用域；不要全局解绑或覆盖用户的 F5。
- 补充条目/空白区/地址栏/终端的快捷键矩阵，尤其检查 Ctrl、Shift 组合键是否被误当作普通复制、剪切或粘贴。
- 诊断只记录键名、修饰键、焦点元素类型、窗口/请求标识，不记录终端输入正文。
- 验收时既确认桌面刷新，又确认**没有**打开调试选择器、运行调试或误操作其他编辑器。

优先级：**P1，下一版首先闭环的已观察问题。**

## 5. 对上一轮优化判断的修正

### 5.1 拖放：特定真实场景已经通过，不应直接重写

本轮使用真实前台鼠标，完成带中文和空格名称的单文件跨窗口移动。此前“高亮但未移动”的历史记录仍应保留，但不能继续把整个拖放能力描述为当前必然失效。

建议先保留现有实现，仅补充：多选、文件夹、图标/详情混合视图、同名目标、拖动期间刷新、快速导航与迟到响应等场景。只有重新获得失败证据，再决定是否引入稳定节点、拖动期间延迟渲染或统一状态管理。

本轮没有验证大文件内容传输或批量移动，也没有进行拖放故障根因修复。

### 5.2 粘贴：先明确快捷键约定，再处理真正错误

本轮对照显示：

- 技能的后台 Ctrl+V 在地址栏没有可靠执行粘贴，产生了字母 `v`；这是注入方式的限制。
- 前台 Ctrl+V 在 Vim 插入模式中被作为控制键处理，画面出现 `^V`。
- 前台 Ctrl+Shift+V 成功贴入同一段中英文多行文本，并完成保存与重新打开核对。

因此优先改善可发现性：在终端提供简短的粘贴提示或明确菜单入口，说明 Ctrl+Shift+V 的用途。**不要为实现 Ctrl+V 粘贴而无差别劫持 Vim 本来的控制键。**

此前静态发现的“输入超限错误与会话终止状态混用”仍值得修复，但本轮没有进行 64 KiB 超限输入或错误后继续输入验证，不能将它写成新增实机复现结果。定位仍为 `remote-terminal.js:209–225` 与 `media/desktop.js:510–535`。

### 5.3 关闭终端与恢复文件：改善提示，不自动清理

在关闭本轮 Vim 会话并刷新 target 后，观察到 `.swp`，界面大小为 12 KB。初始 target 列表只有 `remote-created.txt`；本轮后首次看到了该恢复文件。

这与 Vim 恢复文件、PTY 终止语义有关，但**不能仅凭 `.swp` 推断存在僵尸进程或插件崩溃**。本轮没有独立检查服务器进程树，也没有读取或删除该文件。

建议评估关闭提示或让用户先返回程序自行保存/退出的流程。现有“关闭窗口会结束进程”的设计应清楚表达；不要从后端盲发 `:q!`，也不要自动批量删除 `.swp`。

## 8. 过程中的环境干扰，不混作插件缺陷

1. 技能的截图实现使用屏幕区域捕获：窗口标题命中不保证画面未被遮挡。开始时截图包含前方其他应用，因此暂停，用户将目标窗口置前后才继续。非目标画面不纳入本报告的证据包。
2. 一次后台点击期间光标前后位置不一致，触发护栏；暂停并取得用户明确的前台键鼠测试许可后继续。
3. 收尾时目标标题曾暂时无法枚举。只读查询显示 Code 进程仍存在；现有日志没有提供足以认定插件导致退出的证据。用户恢复窗口后，同一进程的目标窗口重新可见，随后完成文件复核与收尾。此事不计作“插件崩溃”或“已通过断线重连测试”。

后续测试应重新枚举窗口、核对截图与几何，不能复用本轮的进程 ID、坐标或“仍已连接”的假设。
