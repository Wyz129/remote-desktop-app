## 1. 项目是什么，已经做到哪一步

这是运行于 **VS Code workspace 扩展主机**的扩展，不是 Codex 插件，也不是 RDP/VNC 远程桌面客户端。

核心链路：

```text
Webview 桌面 / 虚拟资源管理器 / xterm.js
                    ↕ 消息协议
extension.js：主机识别、路径校验、文件操作、配置、状态
remote-terminal.js：从 VS Code runtime 加载 PTY、管理会话
                    ↕
远程文件系统 / 原生 PTY / VS Code 编辑器与命令
```

当前已具备：真实远程目录浏览与文件操作、多窗口与窗口缩放、详情/图标视图、桌面布局保存、文件符号链接、命令快捷方式、固定应用、Shell/Vim/htop 终端、账号时钟及操作等效命令。

成熟度判断：**已完成真实远程主链路验证的早期产品**，不是需要推倒重来的静态原型；但尚不能据此宣称复杂输入、规模场景、断线恢复及全部平台兼容都已可靠。

应保留的设计边界：

- Remote-SSH 读取失败不能回退到假数据；本地 Demo 与真实远程状态必须可区分。
- 文件操作经过 URI、路径和根目录保护；这不是已全面审计的文件系统沙箱。
- 远程永久删除需要确认，删除符号链接不能递归删除目标。
- 终端与命令快捷方式需要工作区信任；加载配置不能自动执行命令。
- 底栏展示的是等效命令，不重新执行这些文本，也不记录终端键盘输入。
- 关闭终端会结束进程，最小化不结束；不能擅自改成后台托管或自动重启程序。

依据：`HANDOFF.md:17–32,86–139`，`package.json`，`extension.js:57–119,173–189,661–708`。

## 4. 第一梯队：先解决真实交互可靠性

### 4.1 终端：先区分可恢复错误与会话终止

**静态可定位的不一致：**

1. 后端拒绝超过 64 KiB 的单次 `terminalInput`，通过通用异常路径发送 `terminalError`；该拒绝路径没有销毁已有 PTY。
2. 前端将所有 `terminalError` 都视为“终端启动失败”，设置 `record.active = false`。
3. 前端发送输入又要求 `record.active && record.opened`。

因此，若一个已启动终端收到这类可恢复输入错误，源码链路会使界面停止发送后续输入，而 PTY 可能仍在运行。这与历史 Vim 粘贴问题**不能直接划等号**，但应作为下一轮明确的复现与修复目标。

定位：`remote-terminal.js:209–225`；`media/desktop.js:510–535`。当前超限单测检查了拒绝写入，但没有覆盖前端收到该错误后的可继续输入状态，见 `test/terminal.test.cjs:127–140`。

建议：

- 将启动失败、单次输入拒绝、运行中警告、致命错误、正常退出区分为明确的错误码与会话状态。
- 可恢复错误只拒绝当前操作；如必须结束会话，前后端同步结束，不能一端失活另一端继续运行。
- 大段输入如采用分片，应按 UTF-8 字节限制并保持字符、顺序及 bracketed paste 语义；不要简单拆字符串或直接放大上限。
- 先检查 xterm 默认粘贴/IME 链路、VS Code 快捷键与焦点、输入工具行为，再决定修改点。缺少自定义 IME 代码不等于 xterm 不支持中文。
- 不直接修改随包的 xterm 生成文件，不记录真实输入正文作为诊断日志。

建议验收：真实 Shell/Vim 的单键、多行粘贴、中文组合输入；超限后仍能继续操作或明确结束；隔离目录中保存并核对文件内容；关闭窗口后无遗留会话。

### 4.2 拖放：先定位断在哪一层，不急于替换实现

当前桌面图标采用 Pointer Events，资源管理器条目采用原生 HTML Drag and Drop，两套入口最后汇入移动请求：`media/desktop.js:234–263,338–400`。

两条值得核查的线索：

- 原生 `dragover` 的目标高亮没有与 `canMove()` 使用同一判定；高亮本身不证明该目标最终允许移动。
- `renderWindow()` 用 `replaceChildren()` 重建列表，`renderIcons()` 也重建图标；异步目录或配置响应可能在拖动期间替换相关 DOM。**这是候选原因，不是已证实的历史故障根因。**

定位：`media/desktop.js:294–308,319–336,384–399,720–740,1012–1048`。

建议先记录非敏感的事件与状态链：

```text
源条目与选择集 → dragstart → 目标命中 → drop/dragend
→ fileOperation requestId → 后端结果 → 源/目标目录刷新
```

用真实 VS Code Webview 区分输入事件未产生、DOM 被替换、目标判定拒绝、消息未发出或文件操作失败。必要时再采取拖动期间延迟刷新、保留稳定节点或统一拖放状态管理，避免无依据重写。

建议验收：详情/图标视图双向拖动、多选、中文与空格名称、同名冲突、无效目标、拖动中刷新和取消。最终检查真实源/目标文件，只看高亮或请求已发出不算通过。现有 `dragTo()` 用例见 `test/ui.test.cjs:349–373`，它不能替代 Electron/SSH 实测。

### 4.3 等待确认：让用户知道“现在在等什么”

`inspectRemoteDesktop()` 会等待原生创建确认，返回最终状态前没有向 Webview 明确报告“等待用户确认”。前端启动文案仍是“正在读取桌面…”。定位：`extension.js:327–343,592–600`；`media/desktop.html:27`。

另外，配置读取错误和文件操作失败也有在返回状态前等待通知的路径，见 `extension.js:284–290,563–570`；应检查通知交互是否不必要地延迟业务回包。

建议增加明确状态：连接中、读取中、等待创建确认、用户取消、创建失败、就绪。面板提供重新唤起确认或重试入口，但**不绕过原生确认、不自动创建目录**。普通错误通知与业务结果回传解耦。

建议验收：通知进入通知中心后面板仍能解释等待原因；确认、取消、权限失败都进入明确状态，不无限显示“读取中”。这是一项适合作为首轮低风险改进的工作。

## 5. 第二梯队：规模、恢复与数据一致性

### 5.1 先去重刷新，再考虑虚拟列表

源码中有明确的重复读取来源：

- `refreshRemote()` 先读取桌面，随后又遍历包含桌面的 `paths`。
- `refreshAll()` 已把窗口目录交给后端刷新，同时又为非根目录发送 `readDirectory`。
- 文件操作后，后端重读 `affected`；前端收到成功结果后也会重读受影响目录。

定位：`extension.js:362–380,568–572`；`media/desktop.js:779–789,907–922,1041–1046`。

目录读取为全量 `Promise.all(children.map(...stat...))`，前端为全量条目渲染；缓存按浏览路径累积，重建索引时遍历已缓存目录。定位：`extension.js:204–236`；`media/desktop.js:151–159,294–308,720–740`。

建议顺序：

1. 明确刷新由哪一层负责，合并同路径的在途读取，避免重复刷新；保留窗口/requestId 关联，不能退回旧响应覆盖新状态的行为。
2. 对 metadata 读取使用有上限的并发；必要时按需获取元数据。
3. 建立 1,000 项、10,000 项目录的首屏耗时、交互延迟、DOM 数、缓存规模基准，再决定虚拟列表、渐进呈现和缓存淘汰策略。
4. 不在没有基准时承诺性能倍数；运行在 SSH workspace 主机上的 `stat` 不应被简单描述为每项一次跨 SSH 网络往返。

### 5.2 恢复：心跳提示不等于恢复协议

已有 30 秒同步和 90 秒过期提示；这证明的是扩展主机消息响应状态，不是独立 SSH 网络探测。`requestDirectory()` 有请求关联，但未见超时与连接代际管理。定位：`media/desktop.js:92–117,771–777,1096–1098`。

建议：

- 区分等待响应、恢复中、目录过期与终端已结束等状态。
- 管理请求超时、关闭窗口时的待处理请求及重连后的旧响应；保留上次有效内容并清晰标为过期。
- 只读目录请求可按策略重试；**写入、复制、删除和终端输入不能因超时就自动重放**。
- 恢复目录和界面不等于恢复 PTY；保留“不自动重启程序”的安全边界。
- 多项文件操作可能部分成功，宜返回逐项结果；不虚假承诺自动事务回滚。

### 5.3 流控：已有后端保护，下一步看端到端消费

后端已经具有暂停/恢复阈值和 2 MiB 输出上限，不应描述成“完全没有背压”。但当前队列在消息发送完成后减记，前端调用 `terminal.write()`，未将 xterm 消费完成反馈给后端。消息投递完成并不等于终端已消费完毕。

定位：`remote-terminal.js:114–133`；`extension.js:126–128,149–150`；`media/desktop.js:523–535`。

建议先观察持续输出、隐藏面板和多终端时的在途字节及前端队列；必要时引入批量发送与消费确认/字节额度控制，而不是取消上限或随意丢弃 ANSI 输出。

## 6. 工程化方向：小步治理，不做框架迁移

- **版本与回退**：实施前取得最新检查点。可考虑 Git，或继续使用新的日期化备份；本次没有初始化仓库，也没有创建源码备份。
- **兼容声明**：`package.json` 声明 `^1.85.0`，历史实测为 1.137.0。需要验证最低声明版本与计划支持版本；否则应调整支持声明。PTY 依赖内部 runtime 布局，应保留明确诊断与受控兼容处理，不能加载随机原生模块掩盖 ABI 问题。
- **证据可追踪**：自动化产物按版本/运行编号存放，记录运行环境、源码或包哈希、当次 SSH 验证和未覆盖项，避免复用易覆盖的 smoke JSON 充当历史证据。
- **适度拆分**：当前后端 722 行、前端 1,098 行、PTY 243 行。问题主要是职责耦合和消息状态，而非规模迫使重写。随修复逐步抽离终端控制、拖放、导航/刷新与协议校验；可先用 JSDoc/共享协议常量，不要求迁移 React/TypeScript。
- **配置一致性**：现有串行队列和临时文件写入应保留；它们不是跨多个 VS Code 窗口的锁。若出现多实例并行修改，再设计版本冲突检测和合并策略。
- **发行内容**：当前 `.vscodeignore` 没有排除 `docs/**`。后续打包时决定评估文档是否随包分发；本次不修改打包规则、不重建 VSIX。

安全边界仍需持续验证，尤其是符号链接中间路径、批量操作部分失败和并发文件变化。它们属于进一步审查方向，不能从现有词法路径检查推导出“全部场景安全”。
